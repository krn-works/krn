# Irrelevant engineering control

**Topic: component composition.** Start a design system with a token inventory that names each value, intended role, allowed range, and replacement path. Keep raw values in one source file and derive CSS variables during the build. Components should consume shared variables and expose a small public API; local exceptions require a concrete use case and a regression example.

Before changing a composition, read the current component contract and its consumers. Separate global foundations, layout utilities, and component behavior so that a local repair does not silently change unrelated screens. Prefer an existing composition primitive when it expresses the desired spacing or alignment. Avoid adding a second abstraction for a single visual case.

Validate representative widths, text lengths, and states. A successful stylesheet build confirms syntax and asset resolution, but does not establish that a page still matches its design intent. Record the inspected viewport and the source revision beside screenshots. Keep generated variables reproducible and do not hand-edit output files. Remove temporary snapshots after review.

When a token changes, inspect its derived variables and every rendered consumer before merge. Compare component defaults with actual call sites so a new option does not create a second convention. Pin screenshots to the source revision. Remove aliases after consumers move. Document the migration owner and rollback note.
